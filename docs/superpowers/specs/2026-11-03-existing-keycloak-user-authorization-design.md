# 已有 Keycloak 用户授权向导设计

**设计状态：** 方案方向已确认，等待规格审阅。

## 背景

L5 Console 使用 `agentteams` Realm 完成登录。登录令牌中的 `tenant`、`project`、`team` 属性用于构造应用认证主体；Realm 角色经协议映射写入 `permissions` 声明。Control Plane 验证令牌后，再根据 AgentTeams 数据库中的组织管理授权和项目成员关系计算有效权限。

现有页面把相关操作分散在多个位置：身份页维护组织成员和身份映射；角色页可以授予平台/组织管理员，并修改已经存在的项目成员角色，但不能为已有 Keycloak 用户补齐令牌范围或建立项目成员关系。直接在 Keycloak 调角色也不能代替 AgentTeams 的组织/项目授权记录。

L5 中的 `123` 用户已经存在，Keycloak `sub` 为 `f6c40e0f-2118-427e-8098-bd356b6296bc`。其 Keycloak 用户属性缺少 `tenant`、`project`、`team`；数据库中已有一条指向“兼容组织 - tenant-a”的组织 `OWNER` 成员关系，但没有项目成员关系或管理员授权。另有“晓的项目”当前关联 `tenant-a`，而“晓”组织下的租户是“海月”；当前模型无法证明两者属于同一授权范围。

## 目标

- 在管理后台增加独立的“授权已有账号”向导，只操作 `agentteams` Realm 中已存在的 Keycloak 用户。
- 在一个可审阅的流程中设置用户的默认令牌范围、组织成员关系和项目成员角色。
- 让管理员在提交前看清现有授权、变更内容和最终作用范围。
- 由后端校验管理员作用域、组织/租户/项目关系及目标账号状态，完成 Keycloak 与 AgentTeams 数据同步并记录审计。
- 不改密码，不创建新 Keycloak 用户，不读取或展示凭据。

## 非目标

- 不创建 Realm、Keycloak 用户或临时密码；新用户继续使用现有“初始化外部用户”流程。
- 不把组织成员角色、项目角色或 Keycloak Realm 角色混为一种授权。
- 不在本向导中授予平台管理员；平台和组织管理员授权继续走“角色与权限”中的独立管理员授权入口。
- 不自动迁移项目、租户或组织来修复历史范围不一致。
- 不让浏览器直接持有 Keycloak 管理凭据。

## 领域与授权边界

- **Keycloak 登录范围：** 单个默认 `tenant`、`project`、`team`，作为令牌认证主体的上下文，不表示用户已经拥有这些资源的成员权限。
- **组织成员关系：** `organization_memberships` 中的 `OWNER`、`ADMIN`、`MEMBER`、`AUDITOR`。它描述组织成员身份；不能单独替代管理后台中的组织管理员授权。
- **项目成员关系：** `project_memberships` 中的 `OWNER`、`ADMIN`、`OPERATOR`、`DEVELOPER`、`VIEWER`。它决定项目范围内的有效权限。
- **管理后台管理员授权：** 独立的 `management_role_assignments` 记录。平台/组织管理员角色不隐式产生项目成员资格，也不由本向导默认授予。
- **OIDC Subject：** 以 Keycloak 用户 UUID（`sub`）为主体标识；界面显示用户名和 Subject，所有写入均使用 Subject 关联。

## 方案选择

| 方案 | 影响 | 结论 |
|---|---|---|
| 扩展新用户初始化向导，同时处理新账号和已有账号 | 把账号创建、密码交付和已有身份授权混在同一流程 | 不采用 |
| 独立的“授权已有账号”向导 | 不接触密码，明确显示现有账号和授权变更；复用身份/角色数据模型 | **采用** |

## 管理员使用流程

### 1. 查找账号

- 管理员按用户名精确搜索 `agentteams` Realm 中的用户。
- 结果展示用户名、显示名、Subject、启用状态和现有范围属性；不返回密码、Token 或其他凭据。
- 禁用用户不能继续授权；已经存在的映射或成员关系以只读方式列出。
- 查询和授权范围由服务端按平台管理员或本组织管理员权限过滤，不能仅依赖前端隐藏选项。

### 2. 选择默认登录范围

- 必选一个启用的组织、该组织所属的租户、有效项目以及默认工作团队，分别写入 Keycloak 用户属性 `tenant`、`project`、`team`。
- 项目选择器只列出所选租户内的项目；后端再次验证项目与租户、组织关系。
- 提交前显示原属性和新属性。若用户已有其他范围，明确提示这会替换其单一默认令牌范围；不得静默覆盖。
- 当前数据中若项目只能关联到其他租户（例如“晓的项目”与“海月”租户的现状），阻止提交并说明需要先由管理员修复资源归属。
- 默认工作团队仅作为 OIDC 令牌上下文；不能据此自动授予项目或团队资源权限。

### 3. 设置成员关系

- 组织成员角色可选 `MEMBER`、`AUDITOR`、`ADMIN`；若目标组织当前成员是 `OWNER`，必须通过独立所有者流程处理，不允许本向导降级或转移。
- 项目成员角色可选 `VIEWER`、`DEVELOPER`、`OPERATOR`、`ADMIN`。首次加入默认 `VIEWER`；`OWNER` 转移走现有的独立确认流程。
- 可只建立组织成员关系，也可同时建立一个项目成员关系；若选择项目，项目必须属于已选择的组织/租户范围。
- 管理员授权（`PLATFORM_ADMIN` / `ORGANIZATION_ADMIN`）不属于普通成员角色。需要管理后台能力时，管理员离开向导后使用现有管理员授权区单独授予，并明确目标组织。

### 4. 审阅并应用

- 确认页展示用户 Subject、启用状态、原/新 OIDC 范围、组织成员关系、项目成员角色，以及是否会覆盖已有关系。
- 管理员确认后，后端写入 Keycloak 用户属性和所选 AgentTeams 成员关系，记录操作者、目标 Subject、范围、角色和结果。
- 成功页说明用户需要退出后重新登录以获取新令牌；页面不展示任何凭据。
- 重复提交应幂等，不得重复创建成员关系或生成重复审计操作。

## 权限控制

- 平台管理员可为任意组织的用户授权。
- 组织管理员仅可为其管理的组织中的用户授权，不可跨组织搜索或写入。
- 组织成员角色写入要求对应组织管理权限；项目成员写入同时检查项目所属组织/租户及授权者的成员管理权限。
- `OWNER` 转移、平台管理员授权和组织管理员授权不通过普通授权向导隐式完成。
- 前端无权限时隐藏入口并对直接路由显示友好提示；服务端对越权写入返回 403。

## 服务端与数据流

- 增加受保护的后端 API：搜索可管理的 Realm 用户、读取现有授权预览、提交授权变更。
- 后端 Keycloak 客户端只增加必要的 Realm 用户查询和用户属性更新能力；不授予凭据管理或平台级 Realm 管理权限。
- 数据库成员关系通过现有领域服务和仓储维护，不从浏览器直接写数据库，也不以 Keycloak Realm 角色替代 AgentTeams 项目成员权限。
- Keycloak 属性更新与数据库事务跨两个系统，需有明确的幂等键、变更阶段、失败恢复/补偿和审计；部分成功时页面显示待恢复状态，不伪报成功。
- Keycloak 角色映射只用于生成既有 `permissions` 声明；本向导不新增或批量修改 Realm 角色映射。

## 错误处理

- 用户不存在或已禁用：停止流程，显示可操作提示。
- 用户已有不兼容的范围或成员关系：显示变更预览，只有明确确认后才替换可编辑关系。
- 组织、租户、项目状态无效或归属不匹配：拒绝提交，不自动迁移资源。
- Keycloak 更新失败：数据库成员关系不应提交为完成态；数据库写入失败时恢复旧 Keycloak 属性，或持久化可重试的恢复状态。
- 重试同一幂等操作不得重复授权；不同请求复用同一幂等键时返回冲突。
- 错误响应不包含密码、Token、Keycloak 管理凭据或跨组织资源是否存在的敏感信息。

## 验收标准

1. 管理员可以按用户名查找现有 Keycloak 用户，并查看 Subject、状态、当前范围和已有成员关系。
2. 一次确认可以设置默认 OIDC 范围，并新增或更新所选组织/项目成员关系；退出重登后新令牌使用新范围。
3. 项目不属于所选租户/组织时，前端过滤并由后端拒绝直接伪造提交。
4. 普通组织/项目成员授权不会隐式授予组织管理员或平台管理员权限。
5. `OWNER` 转移及管理员角色提升仍要求明确且独立的操作确认。
6. 组织管理员不能查看或修改其他组织用户；平台管理员可跨组织操作。
7. 重复提交幂等；跨系统失败可恢复，审计记录包含授权前后范围和角色，不包含凭据。
8. 用户授权成功后重新登录，身份验证不再因缺少 `tenant`、`project` 或 `team` 令牌属性而返回 401。

- 本规格只定义产品功能，不会直接改动 L5 用户、角色、项目或租户数据。
